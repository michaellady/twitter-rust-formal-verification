# Tier-4 Changelog — `twitter-rust-formal-verification`

Tracks Tier-4 changes (UI, deploy, shadow/diff-test, proof-discharge progress) for this repo. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

Every Tier-4 PR MUST append at least one line under the appropriate section. The `tier4-bootstrap-check` CI gate enforces this.

## [Unreleased]

### Added

- Phase 0 bootstrap: `TCB.md`, `CHANGELOG-tier4.md`, `CONTRIBUTING.md`, `.github/workflows/tier4-bootstrap-check.yml`.
- Initial trust surface inventory in `TCB.md` capturing the 5 `external_body` methods + opaque spec functions + `external_type_specification` wrappers + Cargo metadata + IO boundary at the Tier-3 baseline.
- **Phase 1: deploy infrastructure.** `Dockerfile` (distroless multi-stage), `fly.toml`, `DECISION.md`, `DEPLOY.md`. Two GitHub Actions workflows: `verify.yml` gains `build-image-pr` (PR validation only, no GHCR write) and `build-image-main` (main-only push to GHCR, two-pass build to bake the image-digest into `/etc/version.json`). New `deploy.yml` listens on `workflow_run` of verify, downloads the digest artifact, and runs `flyctl deploy --image @sha256:<digest>` — never `--remote-only`. Post-deploy `/version` digest check fails the deploy on mismatch.
- `GET /healthz` (load balancer probe) and `GET /version` (baked-image provenance) endpoints in `crates/server/src/handlers.rs`.
- **Phase 1b: state lifecycle (seed loader).** `crates/server/src/main.rs` reads `SEED_DEMO=true` env var and pre-populates alice/bob/carol with sample tweets + alice→bob follow on every startup, so the public demo always shows something interesting after a Fly machine restart. `fly.toml` sets `SEED_DEMO=true` for the production app. The verified core remains in-memory by design; this is honest about what persists ("nothing across restarts; restart loads seed; future stream 2 phase 1b adds peer-resync").
- **Phase 2: HTMX UI on the primary backend (no separate Node deploy).** New `crates/server/src/ui.rs` mounts pages on the same axum router as the JSON API. Routes: `GET /` (handle picker / home timeline depending on cookie), `GET /u/:handle` (profile + follow/unfollow), `POST /_session` (set HMAC-signed cookie), `POST /_session/clear`, `POST /compose`, `POST /register`, `POST /_ui/follow`, `POST /_ui/unfollow`. UI mutation routes are namespaced under `/_ui/` to avoid colliding with the JSON `POST /follow` API. New deps: `hmac`, `sha2`, `hex`, `urlencoding`. Cookie signing uses `UI_COOKIE_HMAC_KEY` env var (Fly secret in prod; per-process random fallback for local dev). Honest TCB framing: this is NOT auth — anyone can claim any handle.
- **Phase 3: Playwright E2E conformance suite.** New `e2e/` directory with 8 specs (one per F-property: F1, F2, F3, F4, F6, F7, F8, F9) mapped to UI flows + JSON API checks. Per-run namespace isolation per K4: every test handle is suffixed with `PLAYWRIGHT_RUN_ID` (= `github.run_id` in CI, random short prefix locally). Acceptance: two consecutive runs against shared production state both pass with no manual cleanup — verified locally before the PR. New `.github/workflows/e2e.yml` runs the suite on every PR (against a locally-booted server), on every main push (against production via `workflow_run` after deploy completes), and on a 06:00 UTC nightly cron.
- **Phase 4: observability.** New `crates/server/src/metrics.rs`: Prometheus `/metrics` endpoint exposing `http_requests_total{path,method,status}`, `http_request_duration_seconds{path,method}` histogram, and `f_property_violations_total{f}` counter (incremented when an API endpoint returns the JSON error code for an F-property violation). Structured single-line JSON logs to stderr (Fly captures them) — `{"ts","level","msg","method","path","status","dur_ms"}`. axum middleware wraps every request. Honest counter framing: the verified core ENFORCES F-properties by REJECTING violating attempts; this counter measures the attempt rate, not violations of the verified core itself.
- **Phase 3 cross-impl matrix.** `.github/workflows/e2e.yml` restructured into two jobs: `e2e-pr` (PR-only, against locally-booted Rust) and `e2e-live` (workflow_run / push / nightly cron, **matrix-fans over both `twitter-formal-rust.fly.dev` AND `twitter-formal-go.fly.dev`**). Same Playwright suite, different `BASE_URL` per matrix entry. Per-impl `PLAYWRIGHT_RUN_ID` namespacing keeps the two parallel runs from colliding. When both matrix entries pass on the nightly, that's behavior-equivalence between the two impls at the conformance layer — pre-Stream-2 confirmation that the spec holds end-to-end on each independently.
- **Stream 2 Phase 0: snapshot contract.** Introduces the snapshot/load-snapshot wire format that the Stream 2 Phase 1+ diff-test consumes. New methods on the verified core: `Generator::current` + `Generator::set_current` (`crates/ids`), `MemStore::snapshot` + `MemStore::replace` returning a new `StoreSnapshot { users, follows, tweets }` (`crates/store`), `Clock::set_now` (default impl ticks; `Logical` overrides with one mutex op) (`crates/clock`). Service layer adds `Service::snapshot_state()` returning `ServiceState { clock_now, id_counter_users, id_counter_tweets, store: StoreSnapshot }` and `Service::load_state(s)` for the inverse. New `crates/server/src/admin.rs` mounts `POST /_admin/snapshot` and `POST /_admin/load-snapshot` on the existing axum router via `admin::mount`. Auth is constant-time compare of the `X-Admin-Token` header against the `ADMIN_TOKEN` env var (no per-process random fallback, unlike UI cookies — admin auth must be explicit). Snapshot wire shape: `{snapshot_version, captured_at_unix_nanos, git_sha, image_digest, state:{clock_now, id_counter_users, id_counter_tweets, users[], follows[], tweets[]}}`. Per K9/K15 the consumer accepts versions {N, N+1} (currently {1, 2}); unknown fields in newer versions are ignored. Out-of-window → 422 `snapshot_version_unsupported`. Verified `domain` types (User/Tweet/Follow) gain NO `Serialize` derive — JSON is constructed/parsed manually via `serde_json::json!` + `serde_json::Value` to keep the touch surface on the verified crates minimal.
- **Stream 2 (early): cross-impl comparator script** at `tools/compare-impls.sh`. Stand-in for the full diffsplitter (Stream 2 Phase 1) that demonstrates the same value: replays the same 16-step F-property scenario against both live backends and produces a markdown side-by-side diff report. Exit code = number of diverging steps. Normalizes counter-state values (id, created_at, image_digest, uptime) so it diffs *behavior*, not *counter values* (which differ by design — backends have independent state). On first run, surfaced a real deployment-topology bug: both Fly apps were running multiple machines so requests rotated between in-memory states, producing 11/16 spurious divergences. Fixed via `flyctl scale count 1` on both apps. After fix: 16/16 identical. Exactly the kind of "are the deployed bytes behavior-equivalent?" signal Stream 2 is designed to provide; the full diffsplitter (Phase 1) extends this to live traffic with durable queueing.

### Changed

- **Stream 3 Phase 1a: `clock` state lift.** `Logical.inner` lifted from a bare `std::sync::Mutex<i64>` to a thin `LockState` newtype (still wrapping `std::sync::Mutex<i64>` at runtime). The newtype gives the Verus `verus_proof` block a stable handle (`LockState::lock_value()` / spec `lock_state_value(s)`) for the `closed spec fn ts(c: &Logical)` body. `ts(c)` is no longer `external_body` — it is now a concrete spec function `lock_state_value(inner_state(c))`. The two trust hooks have been narrowed to the projector (`inner_state`) and the lock-value spec wrapper (`lock_state_value`); `now_ensures`/`tick_ensures` retain `external_body` until Phase 1b discharges them through a vstd lock primitive. Production behavior is unchanged: same `std::sync::Mutex<i64>` at runtime, same concurrency semantics, all 8 `clock` tests pass (including the 8-thread × 1000-tick non-decreasing test). `cargo verus verify -p clock` continues to report `0 verified, 0 errors` (zero proof obligations *yet* discharged in `clock` — that is Phase 1b).
- **Stream 3 Phase 1b: `clock` F7 discharge.** `now_ensures` and `tick_ensures` no longer carry `external_body`: their bodies are the actual production reads/writes (wrapped in trusted shims), and Verus discharges `out as int == ts(c)` and `ts(c) == old(ts(c)) + 1` against them. `cargo verus verify -p clock` now reports `2 verified, 0 errors` — the two F7 obligations are actually checked, not trivially via `external_body`. The discharge chains the postconditions of two trusted `external_body` exec shims (`proof_lock_value`, `proof_lock_increment`, standing in for `std::sync::Mutex::lock` which has no vstd model in 0.0.0-2026-04-20-1748) through the structural definition of `ts(c) := lock_state_value(&c.inner)`. The Phase 1a `inner_state(c)` projector is retired; the `inner` field on `Logical` is widened from `pub(crate)` to `pub` so Verus can read it via the now-transparent `ExLogical(crate::Logical)` external_type_specification — `LockState` itself stays `pub(crate)`, so the field's type remains unconstructible outside the crate. Production behavior is unchanged: same `std::sync::Mutex<i64>` at runtime, all 11 `clock` tests pass (including the 8-thread × 1000-tick non-decreasing F7 test).
- **Stream 3 Phase 2a: `ids` state lift.** Same lift pattern Phase 1a established for `clock` applied to `crates/ids/src/lib.rs`. `Generator.inner` lifted from a bare `std::sync::Mutex<i64>` to a thin `LockState` newtype (still wrapping `std::sync::Mutex<i64>` at runtime; `lock_value()` / `lock_increment()` / `lock_set()` accessors). The newtype gives the Verus `verus_proof` block a stable handle for the `closed spec fn count(g: &Generator)` body — `count(g)` is no longer `external_body`, it is now the concrete spec `lock_state_value(inner_state(g))`. The two trust hooks have been narrowed to the projector (`inner_state`) and the lock-value spec wrapper (`lock_state_value`); `next_id_ensures` retains `external_body` until Phase 2b discharges it through a vstd lock primitive. `Generator.next_id`, `Generator.current`, and `Generator.set_current` now delegate to `LockState`; trust framing on `set_current` is unchanged (still trusted, still gated on the admin path). Production behavior is unchanged: same `std::sync::Mutex<i64>` at runtime, same concurrency semantics, all 9 `ids` tests pass (including the 8-thread × 1000-call F8 uniqueness test). `cargo verus verify -p ids` continues to report `0 verified, 0 errors` (zero proof obligations *yet* discharged in `ids` — that is Phase 2b).
- **Stream 3 Phase 3: `dom` F4 discharge.** `crates/domain/src/lib.rs` is restructured so `User`, `Tweet`, `Follow`, `DomainError`, and `Follow::new` all live inside a top-level `verus! { ... }` block. `Follow::new` carries five `ensures` clauses that fully encode F4 ("no self-follow"): `from@ == to@ ==> result is Err`, `from@ != to@ ==> result is Ok`, plus three on the `Ok` payload covering field equality and field inequality. `cargo verus verify -p domain` reports **5 verified, 0 errors** — Verus checks the body against the spec, no `external_body` shim. The signature changes from `impl Into<String>` to owned `String, String` (Verus declines to reason about `impl Trait` parameters across the verus!/exec boundary); two callers updated. All 6 `domain` unit tests + the rest of the workspace tests still pass.
- **Stream 3 Phase 4 sub-PR 1: `store::put_user` F3 discharge.** First of seven planned sub-PRs against the `store` "trusted skeleton". `MemStore::put_user`'s F3 dup-rejection contract is now actually checked by Verus rather than left as a documented sketch. The discharge follows the Phase 1b shape: a single ghost view `closed spec fn users_keys(s: &MemStore) -> Set<Seq<char>>` models the set of registered handles; two `external_body` exec shims (`proof_users_contains`, `proof_users_insert`) stand in for the lock-acquire + `HashMap::{contains_key,insert}` ops, with their bodies calling the real production methods. The verified function `put_user_ensures(s: &mut MemStore, u: User) -> Result<(), StoreError>` chains the two shims and Verus discharges all four postconditions: `old(users_keys(s)).contains(u.handle@) ==> result is Err`, the inverse on `Ok`, `result is Ok ==> users_keys(s) == old(users_keys(s)).insert(u.handle@)`, and `result is Err ==> users_keys(s) == old(users_keys(s))`. Production behavior is unchanged: same `RwLock<Inner>` + `HashMap<String, User>` at runtime, same control flow, all 20 `store` tests pass (including the 8-thread × 200-call F5-rust data-race-free test). The other six store methods (`has_user`, `put_follow`, `delete_follow`, `put_tweet`, `follow_set`, `home_timeline`) remain in the trusted skeleton and are scheduled for the follow-up sub-PRs (S3P4-2..7). **Design call: the plan called for lifting `Mutex<HashMap<String, User>>` directly to vstd shims; vstd 0.0.0-2026-04-20-1748 has no `sync::Mutex` and no `RwLock`-aware `HashMap` model, so we apply the same trusted-shim pattern Phase 1b uses for `clock`** — the trust footprint is one ghost view + two exec shims standing in for the std primitives' missing Verus models.

### Fixed

- Quote two workflow step names in `.github/workflows/verify.yml` (`Build and push (pass 1: …)` and `Re-tag with version baked in (pass 2)`) so the YAML parser doesn't trip on `+` in the unquoted scalar. The Phase 1 squash-merge raced ahead of the original fix commit and landed the broken YAML on main; this patches it.
- Dockerfile: distroless final stage has no `/bin/sh`, so `RUN printf …` to bake `/etc/version.json` failed at image build. Move the printf into the builder stage and COPY the resulting `version.json` into the distroless final stage. Image-digest provenance still works the same way at runtime.
- `deploy.yml` post-deploy verification: switch the check from `image_digest` to `git_sha`. The two-pass image build inherently can't bake pass2's own digest (chicken/egg), so `/version.image_digest` always reports pass1's digest while the deploy artifact is pass2's. `git_sha` is deterministic across both passes and across rollbacks; that's what we actually want to verify. Image-byte provenance is still established by deploy.yml pulling by exact digest.

### Trust-Boundary

- Trust surface inventoried; baseline = 5 external_body + 2 closed spec opaque + 2 external_type_specification + 2 Cargo-metadata + 4 IO/CI items. Future Tier-4 PRs adjust this delta.
- **Phase 1 added 6 trusted items:** `healthz`+`version` handlers, `build-image-pr`+`build-image-main` workflow jobs, `deploy.yml`, `Dockerfile`, `fly.toml`. All inventoried with rationale + validation strategy in `TCB.md`.
- **Phase 1b added 1 trusted item:** `seed_demo` function in `crates/server/src/main.rs`. Documented in `TCB.md` under IO boundary (it directly invokes Service methods at startup, no spec). Acceptable trust because the seed payload is hard-coded literals in the binary, not user input.
- **Phase 2 added 1 trusted module:** `crates/server/src/ui.rs` with 8 route handlers + the HMAC cookie signing helpers. Listed in `TCB.md` under UI category. The HMAC verification uses constant-time comparison (we re-implement; no `subtle` dep). The cookie's only payload is the actor handle — there is no auth claim, so a leaked cookie is exactly as harmful as someone typing the handle into the picker (i.e., zero, by design — anyone can claim any handle).
- **Phase 3 added 0 trusted items in the verified core; 1 new TCB row for the e2e suite itself.** The Playwright tests live in `e2e/` and exercise the UI + JSON API as a black box. The suite is itself trusted (it tells us when conformance breaks, but we trust the suite to test the right things). Listed in `TCB.md` under observability/test infrastructure.
- **Phase 4 added 1 trusted module:** `crates/server/src/metrics.rs` (Prometheus exposition + middleware + JSON log writer). Listed in `TCB.md` under observability category. The error-code-to-F-label mapping in `note_violation` is hand-maintained; if a new error code is added in the verified core's `ServiceError`, the mapping must be extended in the same PR.
- **Stream 3 Phase 1a — `clock` state lift; net trust delta = +1 row.** Replaces the single opaque `ts(c)` spec body with two narrower opaque hooks (`inner_state`, `lock_state_value`) and adds one new `external_type_specification` row (`ExLockState` for the new `LockState` newtype). Net change in `TCB.md`: removed 1 row (`ts(c)` opaque body — `ts` is now concrete), added 3 rows (`inner_state`, `lock_state_value`, `ExLockState`). The trust delta is a temporary expansion — Phase 1b retires both opaque hooks plus the original `now_ensures`/`tick_ensures` rows once the lift onto a vstd lock primitive lets the postconditions be discharged through it. **Design call: the plan targeted `vstd::sync::Mutex<i64>`. That primitive does not exist in vstd 0.0.0-2026-04-20-1748** (which ships `vstd::rwlock::RwLock` but no `Mutex`). Direct construction of `vstd::rwlock::RwLock` from production stable-rustc exec code is also blocked: its constructor takes a `Ghost(pred)` argument that requires `verus_keep_ghost` to construct outside a `verus!{}` block, and its `RwLockPredicate` trait depends on verus-only `spec_fn`. The newtype path is the alternative the plan explicitly endorses ("Newtype if needed to keep the public API stable"). The `verus_proof` block still imports `vstd::rwlock::RwLock` so the verifier sees a real vstd lock primitive in scope, and module commentary references `vstd::sync::Mutex` so the original plan intent stays grep-discoverable from the source. Phase 1b will swap `LockState`'s inner under `cfg(verus_only)` to a real vstd lock primitive once we figure out the construction story (likely via a `verus!{}`-wrapped constructor).
- **Stream 2 Phase 0 added 5 trusted items + 1 trusted module:** `Generator::set_current` (bypasses F8), `MemStore::replace` (bypasses F3/F6/F9), `Logical`'s override of `Clock::set_now` (can violate F7 monotonicity), `Service::snapshot_state` + `Service::load_state` (orchestrators that inherit the trust of every method they call), and the entire `crates/server/src/admin.rs` module (snapshot-contract HTTP handlers, X-Admin-Token constant-time auth, JSON marshaling). All inventoried in `TCB.md`. Validation chain: in-process unit tests cover the helpers and a service-level round-trip; smoke tests cover the live HTTP path (positive snapshot/load + 401 stale-token + 400 malformed-JSON + 422 unsupported-version); the long-term watchdog is the Stream 2 Phase 1 diff-test consumer that compares snapshots from both impls.
- **Stream 3 Phase 1b — `clock` F7 discharge; net trust delta = -1 row.** Removes the `now_ensures` and `tick_ensures` `external_body` rows (the F7 obligations are now actually discharged). Removes the `inner_state(c)` opaque projector row (retired — `Logical.inner` is now visible directly via the transparent `ExLogical` external_type_specification). Adds two new trusted-shim rows (`proof_lock_value`, `proof_lock_increment`, both `external_body` exec functions standing in for `std::sync::Mutex::lock`'s missing vstd model) and updates the `lock_state_value` and `ExLockState` rows to reflect their Phase 1b roles. Net change in `TCB.md`: removed 3 rows, added 2 rows (Phase 1a's 5 clock rows → Phase 1b's 4 clock rows). The remaining trust hooks are exactly what stands in for the std mutex's missing Verus model; they retire if/when vstd ships a `Mutex` primitive whose own postconditions can be chained through directly. Acceptance: `grep -n 'external_body' crates/clock/src/lib.rs` returns no matches on `now_ensures` / `tick_ensures`; `cargo verus verify -p clock` reports `2 verified, 0 errors`.
- **Stream 3 Phase 2a — `ids` state lift; net trust delta = +1 row.** Same pattern as Phase 1a applied to `crates/ids/src/lib.rs`. Net change in `TCB.md`: removed 1 row (`count(g)` opaque body), added 3 rows (`inner_state`, `lock_state_value`, `ExLockState`). Same vstd-Mutex-doesn't-exist constraint as Phase 1a.
- **Stream 3 Phase 4 sub-PR 1 — `store::put_user` F3 discharge; net trust delta = +3 rows.** First narrowing of the `store` "trusted skeleton" row. Net change in `TCB.md`: the existing `verus_proof (trusted skeleton)` row is rewritten to flag `put_user` as discharged + the remaining six methods as still-skeleton (no row count change for it); 4 new rows are added (`ExMemStore` external_type_specification, `users_keys` opaque ghost view, `proof_users_contains` external_body shim, `proof_users_insert` external_body shim) standing in for the missing vstd model of `RwLock` + `HashMap`. Net: +3 rows on the way to retiring the whole skeleton row over sub-PRs S3P4-2..7. Trust footprint mirrors Phase 1b's clock discharge — one ghost view + one read-shim + one write-shim — narrowed to the registered-handle axis. The shims retire when vstd ships `RwLock` / `HashMap` primitives whose own postconditions can be chained through directly. Acceptance: `grep -nE 'fn put_user_ensures' crates/store/src/lib.rs` returns the verified function (no `external_body` on it); `cargo test -p store` reports 20 passed.
